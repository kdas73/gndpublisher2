# Observability And Error Handling

This document defines the logging, error handling, and health/metrics conventions established by task 015. See [`security.md`](security.md) for the rules on what must never be logged.

## Logging Conventions

- Logging facade: SLF4J, obtained per class as `private static final Logger LOGGER = LoggerFactory.getLogger(X.class)`.
- Correlation ids are attached via MDC using `com.gnd.publisher.logging.LoggingContext`, a try-with-resources helper around `MDC.putCloseable` that restores prior values on close, including during exception unwind.
- MDC key set, defined in `com.gnd.publisher.logging.LogFields`:
  - `runId` - one per scheduled pipeline run (ingestion, publication, cleanup, digest).
  - `sourceId` - RSS source being processed.
  - `newsItemId` - news item being classified.
  - `semanticEventId` - semantic event being published.
  - `publicationId` - publication record being sent to Telegram.
- Run ids are generated by `com.gnd.publisher.logging.RunIdGenerator.generate(stage, clock)`, producing `"<stage>-<instant>-<8charUuid>"`. Every scheduler (`FeedIngestionScheduler`, `PublicationScheduler`, `CleanupScheduler`, `ImportantNewsDigestScheduler`) gets a run id for every invocation, not just ingestion (which is where this pattern originated via `NewsItem.processingRunId`). Only the ingestion run id is persisted to `news_items.processing_run_id`; the publication/cleanup/digest run ids exist purely to correlate log lines within `PipelineRunSupport.run` and are not persisted anywhere.
- The console log pattern (`application.yml`, `logging.pattern.console`) includes `runId` from MDC on every line. Finer-grained ids (`sourceId`, `semanticEventId`, `publicationId`, `newsItemId`) are inlined into log messages at the point they're known rather than added to the global pattern, keeping console output readable.
- Optional future upgrade: Spring Boot 3.4+ supports zero-dependency structured JSON logging (`logging.structured.format.console: ecs`), which would automatically include all MDC keys as JSON fields. Not enabled today - it only pays off once a log aggregator exists (see task 014), so enabling it now would be speculative.

## Error Handling Conventions

Rule of thumb: **catch at the narrowest boundary that lets sibling work continue.**

| Exception | Thrown by | Caught at |
|---|---|---|
| `FeedReadException` | RSS integration layer | `FeedIngestionService.ingestSource` (per-source) |
| `OpenAiIntegrationException` | OpenAI integration layer | `CategorizationService.classifyOne` (per-item), `PublicationContentService` |
| `TelegramPublishException` | Telegram integration layer | `PublicationService.publishToChannel` / `ImportantNewsDigestService.sendDigest` (per-channel) |
| Spring `DataAccessException` hierarchy | Repository/JPA calls | Wherever it surfaces inside the nearest boundary above, or `PipelineRunSupport.run` as the last resort |

- `com.gnd.publisher.logging.PipelineRunSupport` is the single scheduler-level backstop, wired into all 4 schedulers. It assigns the run id, logs start/completion, and catches any `Exception` that escapes the per-item/per-step boundaries so it's logged with `runId` context instead of falling through to Spring's default scheduled-task error handler. It is a diagnosability backstop, not the primary isolation mechanism - the per-item/per-step boundaries remain the first line of defense.
- `PublicationService.publishSelectedContent()` guards `telegramChannelSyncService.syncConfiguredChannels()` in a try/catch: channel sync only upserts DB rows from static config, so on failure, publication proceeds using whatever channel rows already exist rather than aborting the whole run.
- **No custom `DatabaseAccessException` was introduced.** Spring's `DataAccessException` hierarchy is already unchecked and a subtype of `RuntimeException`, so it's already caught correctly by every existing per-item/per-step boundary (all of which catch `RuntimeException`). The only gaps were DB calls made *outside* those boundaries, and those are now covered by `PipelineRunSupport` and the `publishSelectedContent` fix above. A parallel custom exception with no construction sites would be pure ceremony - don't reintroduce this question without a concrete new use case.

## Health, Readiness, Liveness

- `application.yml` sets `management.endpoint.health.probes.enabled: true`, which auto-exposes `/actuator/health/liveness` and `/actuator/health/readiness` health groups (Spring Boot 3 feature), and `management.endpoints.web.exposure.include: health,info,metrics` exposes them over HTTP.
- This app has no REST controllers; actuator's HTTP endpoints require `spring-boot-starter-web` (added as part of task 015 - previously the app had `WebApplicationType.NONE` with no embedded server at all, making the existing health-probe config inert).
- No custom `HealthIndicator` bean was added. Boot's auto-configured `DataSource` indicator already covers the only meaningful readiness signal for this batch app. Deliberately **do not** add OpenAI/Telegram health indicators: a transient external outage should not flip the pod to NotReady and get it killed/restarted by Kubernetes, since the whole point of the per-item error boundaries above is tolerating exactly that kind of failure without treating it as a pod-level failure.
- Task 014 (Docker/K8s, not yet implemented) will wire `/actuator/health/liveness` and `/actuator/health/readiness` into the Kubernetes probe configuration.

## Metrics

- `/actuator/metrics` is exposed, giving JVM memory/GC/uptime, scheduled-task, and datasource pool metrics for free via the actuator dependency already on the classpath.
- No Prometheus/Micrometer registry exporter is configured. That's for scraping/dashboards, not for the "minimal metrics available" deliverable, and is deferred until there's an actual metrics backend to export to (likely alongside task 014).

## Secret And Payload Redaction

- Exception messages thrown by `HttpOpenAiClient`/`HttpTelegramBotClient` are built only from response error fields (truncated to 1000 characters via `MAX_ERROR_BODY_LENGTH`), never from the outbound request JSON, the `Authorization` header, or the bot token embedded in the request URI.
- `ClassificationRun.rawResponse` is persisted to the database for audit purposes only and must never be passed to a logger.
- Regression tests enforce this: `HttpOpenAiClientTest.doesNotLeakApiKeyOrRequestPayloadIntoExceptionMessageOnHttpError` and `HttpTelegramBotClientTest.doesNotLeakBotTokenIntoExceptionMessageOnTelegramError` assert the configured secret literals never appear in thrown exception messages.
